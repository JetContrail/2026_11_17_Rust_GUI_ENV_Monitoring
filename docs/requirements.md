# 統合管理ソフトウェア 要求仕様 (案) v0.1

ステータス: **PO 承認待ち** (§8 の確認事項が決まり次第 v0.2 として確定する)

## 1. 目的

Windows ベースで **入退室管理・環境監視・鍵管理** を一元管理する統合管理ソフトウェアのプロトタイプを作る。
機能イメージは中央電子 [Acsaran-DX](https://www.cec.co.jp/product/security/acsaran-dx)。

- 様々な管理端末をワンストップで管理・監視する (個別システムの一元化によるコスト削減)
- 各種取得データから設備故障などを事前に検知する
- システム間の連係制御 (例: 部屋の入室履歴がないとラック扉を開けられない)
- クラウド連携 (WebAPI による上位連携、既設クラウド端末の利用、ログイン権限があれば場所を選ばずアクセス)

## 2. 規模目標

| 項目 | 目標 |
|------|------|
| ユーザ数 | 最大 200,000 人 |
| オブジェクト数 | 最大 5,000 個 (扉・リーダ・センサ点・接点・鍵・コンセントなど、監視画面上に配置する管理単位) |
| 対象 | 小規模 (扉数枚) から大規模まで同一ソフトで対応 |

## 4. 機能要件

### 4.1 入退室管理 (必須)

| ID | 要件 |
|----|------|
| AC-1 | 入退室用カードリーダからの電文を受信・解析する (リーダ ID、カード ID、時刻) |
| AC-2 | 解錠可否を照合し、許可されていれば電気錠へ解錠指令を出す。拒否時は記録してリーダへ拒否を返す |
| AC-3 | 電気錠の状態 (施錠 / 解錠 / 通信断 / 故障) を GUI に表示する |
| AC-4 | ドアセンサでドア状態 (閉 / 開) を監視する |
| AC-5 | ドア開が一定時間以上継続したら、**警報音** で周囲に知らせ、GUI 上の **ドアアイコンを赤く点滅** させ、警告を出す |
| AC-6 | 入退室・警報・操作の履歴を保存し、検索・表示できる |

### 4.2 監視画面 (必須)

| ID | 要件 |
|----|------|
| SC-1 | 顧客ごとの **下絵** (フロア図など) を読み込み、監視画面の背景にする |
| SC-2 | GUI 本体は全顧客共通とし、カスタマイズは **スクリプト等の読込** でオブジェクト表示を行う |
| SC-3 | **監視画面作成機能** (エディタ) を含む: 下絵の設定、オブジェクトの配置・移動・削除、機器の点との紐付け、保存 |

### 4.3 任意機能 (接続機器がある場合に有効)

| ID | 要件 |
|----|------|
| EM-1 | 環境監視: 温度・湿度・電圧・電流の計測値表示としきい値警報、接点入力監視、接点出力操作 |
| KM-1 | 鍵管理: 鍵保管器の鍵の在庫 / 持出状態、持出・返却履歴 |
| PD-1 | PDU: 電流・電力の監視、コンセントの遠隔 ON/OFF |
| GC-1 | ゲートコントローラ経由の構成: PC / 回線障害時もゲートコントローラ側で照合を継続し、復旧後に履歴を回収 |
| IL-1 | 連係制御: 入室履歴を条件にラック扉の解錠を許可するなど |
| API-1 | WebAPI による上位 / クラウド連携、リモートからのログインアクセス |

## 5. 非機能要件

| 項目 | 要件 |
|------|------|
| OS | Windows 10 / 11 Pro、Windows Server 2019 / 2022 (x64) |
| ネットワーク | Ethernet / IP |
| 暗号化 | 通信暗号化必須。平文通信は既定で拒否する (フェイルクローズ) |
| 耐故障 | 通信断の検知と自動再接続。1 台の機器障害が他機器の監視に影響しない |
| テスト | 機器なしでも `cargo test` で照合・状態遷移・画面表示を検証できる (機器シミュレータを用意) |

## 6. 実機プロトコルと暗号化の課題

公開情報の範囲では、実機と本ソフトの間の電文仕様が分からない。

- SS2279VHC・PS-XGCube・SS2280BL-E の上位通信 (CEC-LAN 含む) は独自仕様で、公開資料に記載がない
- ND シリーズの SNMP v1/v2c は平文のため、そのままでは「通信暗号化必須」を満たさない (ND-IOTR は IPsec、ND-EW04E は HTTPS で対応できる可能性がある)

このため、プロトタイプでは機器との通信を **機器アダプタ** の後ろに隠し、まず暗号化した自前の電文仕様と機器シミュレータで実装する案を §8 Q1 で確認する。

## 8. 仕様確認事項

各項目に推奨案を付ける。

| # | 確認事項 | 推奨案 |
|---|----------|--------|
| Q1 | 実機の電文仕様 | P1 は自前の電文仕様 (TLS 上) と機器シミュレータで実装する。実機は仕様入手後にアダプタを追加する |
| Q2 | 暗号方式 | TLS 1.3 (rustls) + 相互認証 (クライアント / 機器の双方を証明書で認証、自前 CA 発行) |
| Q3 | P1 の構成 | サーバ兼クライアントの単一 Windows アプリ。後でサーバを分離できるようにクレートを分ける |
| Q4 | データ保存 | SQLite (アプリに同梱、追加インストール不要) |
| Q5 | スクリプト言語 | Rhai (Rust 製の組込みスクリプト。ファイル・ネットワークへのアクセスを持たないサンドボックス) |
| Q6 | 画面定義と下絵 | 画面定義は JSON (エディタが保存)、下絵は PNG / JPEG |
| Q7 | ドア開放警報 | 既定 30 秒 (扉ごとに変更可)。警報音はオペレータの「確認」で停止、赤点滅はドアが閉じるまで継続 |
| Q8 | 解錠時間 | 解錠指令後 既定 5 秒で自動施錠 (扉ごとに変更可) |
| Q9 | P1 の照合ルール | 登録済みカード + 扉ごとの通行権限 + 有効期間。時間帯制限・テンキー暗証・生体認証は後続フェーズ |
| Q10 | 不正開扉 (解錠指令なしのドア開) | P1 に含め、開放警報と同じ表示で警報する |
| Q11 | オペレータのログイン | P1 では省略し、P4 (リモートアクセス) と合わせて実装する |
| Q12 | 規模目標の確認方法 | P1 から 20 万ユーザでの照合と 5,000 オブジェクト描画の性能テストを入れる |
